실시간 파이프라인에서 스케줄러가 무거운 작업을 돌릴 때 생기는 문제를, 최소 코드로 재현하고 단계별로 해결한 기록이다.

## 스케줄러에서 무거운 작업을 처리할때 문제점

스케줄러에서 무거운 작업을 실행할때 가장 큰 문제는 점유이다. 스케줄러의 스레드(Pool)을 수동으로 수정하지 않는다면 기본적으로 1개로 설정되어있는데,
이 때문에 작업이 무겁다면 그 작업이 끝나기 전에 모든 스케줄러 작업은 진행이 안된다.

예를들어 `@Scheduled(fixedDelay = 500)`으로 잡아두면 0.5초마다 돌 거라고 기대한다.
그런데 안에서 1초짜리 작업을 하면 그 기대가 깨진다. 때문에 스케줄러의 시간을 단축시켜놔도 그 시간을 보장받기 힘들다.

<br />

### 1. 재현 — 주기가 안 지켜진다

**실행 코드**

```java
  private static void heavyTask() throws InterruptedException {
      Thread.sleep(1000);   // 1초 걸리는 작업을 흉내 낸 것
  }

  @Scheduled(fixedDelay = 500)
  public void dispatch() throws InterruptedException {
      System.out.println("실행시간 :" + LocalTime.now());
      heavyTask();
  }
```

**결과 값**

```bash
  실행시간 :11:14:33.650326
  실행시간 :11:14:35.159509   // +1.509초
  실행시간 :11:14:36.669838   // +1.510초
  실행시간 :11:14:38.186307   // +1.516초
  실행시간 :11:14:39.694201   // +1.507초
  실행시간 :11:14:41.200133   // +1.505초
```

결과값이 전부 1초 이상 차이가 난다. `@Scheduled(fixedDelay = 500)`로 잡아두어도 말이다.

<br />

### 2. 원인

#### 진짜 이유는 fixedDelay

`fixedDelay`는 **이전 실행이 끝난 뒤부터** 시간을 센다.

```text
  [작업 1000ms][대기 500ms][작업 1000ms][대기 500ms] …
  └──────── 1500ms 주기 ────────┘
```

로그의 1.509초가 정확히 이 값이다. 버그가 아니라 정의대로 동작한 것이다.

<Callout type="tip" label="핵심:">
  `fixedDelay`는 **주기를 보장하는 게 아니라 간격을 보장**한다. 주기를 지키고 싶었다면 애초에 기대가 잘못됐다. 작업이 주기보다 오래 걸리는 순간, 주기라는 개념 자체가 성립하지 않는다.
</Callout>

### 3. Executor로 분리 — 주기가 돌아왔다

작업을 스케줄러 스레드 밖으로 내보내면 둘 다 해결된다.

결과값이 전부 1초 이상 차이가 나는 이유는 결국 스레드를 멀티로 사용하지 않기 때문이다. 그래서 처음 돌아간 스케줄러가 스레드를 1초이상 점유하기때문데 다음 스케줄러가 돌지 못한다.
그런데 `Executor`를 사용하면 스케줄러를 가동하는 스레드에서 작업을 처리하지 않고 다른 스레드로 작업을 넘긴후에 다시 환원된 리소스로 스케줄러를 돌린다.

**실행 코드**

```java
  private final ExecutorService executorService = Executors.newSingleThreadExecutor();

  private static void heavyTask() throws InterruptedException {
      Thread.sleep(1000);
  }

  @Scheduled(fixedDelay = 500)
  public void dispatch() {
      System.out.println("실행시간 :" + LocalTime.now());

      executorService.submit(() -> {         // 맡기고 즉시 반환
          try {
              heavyTask();
          } catch (InterruptedException e) {
              log.warn("error={}", e.getMessage());
          }
      });
  }
```

**결과 값**

```bash
  실행시간 :11:22:37.404029
  실행시간 :11:22:37.906174   // +0.502초
  실행시간 :11:22:38.410314   // +0.504초
  실행시간 :11:22:38.915853   // +0.505초
  실행시간 :11:22:39.421966   // +0.506초
  실행시간 :11:22:39.927513   // +0.505초
```

0.5초 주기가 그대로 지켜진다. `submit()`은 작업을 큐에 넣고 **기다리지 않고 바로 반환**하기 때문에, `dispatch()`는 몇 마이크로초 만에 끝난다.

<Callout type="warning" label="함정:">
  주기는 지켜졌는데, 이 순간 **보장의 출처가 바뀌었다.**
`@Scheduled`가 지켜주던 "겹치지 않음"은 **메서드 본문**에 적용된다. 그런데 `submit()`을 쓰면 본문은 즉시 끝나고 실제 작업은 본문 밖에서 돈다. 
2장에서 확인한 그 보장이 더는 작업에 닿지 않는다. 지금도 작업끼리 겹치지는 않는다. 
다만 그건 `@Scheduled` 덕분이 아니라 **`newSingleThreadExecutor()`를 골랐기 때문**이다. 
이 한 줄을 `newFixedThreadPool(4)`로 바꾸면 작업 4개가 진짜로 동시에 돈다. 컴파일도 되고 로그도 멀쩡하다. **아무도 경고해주지 않는다.**
</Callout>

<br />
### 4. 그런데 큐가 쌓인다

생산과 소비의 속도가 다르다.

```text
  생산 : 0.5초에 1건  (dispatch)
  소비 : 1.0초에 1건  (워커 스레드 1개)
```

1초마다 1건씩 밀린다. 10초면 20건 제출 · 10건 처리 · **10건 적체**다. 하루 돌리면 43,200건이 큐에 남는다.

`newSingleThreadExecutor()`의 내부 큐는 `LinkedBlockingQueue`이고 **용량 제한이 없다.** 거부하지도, 기다리게 하지도 않고 무한정 받는다.

#### 눈으로 확인하기

큐 크기를 보려면 `ThreadPoolExecutor`로 직접 만들어야 한다. `newSingleThreadExecutor()`는 반환값을 래퍼로 감싸서 `getQueue()`에 접근할 수 없다.

```java
import java.util.concurrent.LinkedBlockingQueue;
import java.util.concurrent.ThreadPoolExecutor;   // ★ Tomcat 것이 아님에 주의
import java.util.concurrent.TimeUnit;

private final ThreadPoolExecutor executorService =
    new ThreadPoolExecutor(1, 1, 0L, TimeUnit.MILLISECONDS, new LinkedBlockingQueue<>());

@Scheduled(fixedDelay = 500)
public void dispatch() {
    processTimes += 1;
    int taskId = processTimes;              // ★ 지역 변수 스냅샷 (이유는 5장)

    executorService.submit(() -> {
        try {
            Thread.sleep(1000);
            System.out.println("task " + taskId
                + " 실행 | 현재 pt=" + processTimes
                + " | 큐=" + executorService.getQueue().size());
        } catch (Exception e) {
            log.error("error ={}", e.getMessage());
        }
    });
}
```

**결과 (16번째 작업 시점)**

```bash
task 16 실행 | 현재 pt=32 | 큐=16
```

<Callout type="error" label="에러:">
  작업이 **버려지는 게 아니라 쌓인다.** 큐는 FIFO라 전부 실행된다. 다만 점점 늦게.
  task 100은 50초 시점에 제출돼 100초 시점에 실행된다. **지연이 선형으로 늘고, 복구되지 않는다.** 생산이 소비보다 빠른 한 영원히 따라잡을 수 없다.
</Callout>

<br />
### 5. 측정하다 만난 함정 — 람다는 필드를 늦게 읽는다

여기서 한참 헤맸다. 처음엔 `taskId` 없이 이렇게 찍었다.

```java
private int processTimes = 0;

@Scheduled(fixedDelay = 500)
public void dispatch() {
    processTimes += 1;
    executorService.submit(() -> test(processTimes));   // ← 필드를 직접 참조
}
```

**출력**

```bash
1
2
4
6
8
10
```

숫자가 2씩 뛴다. **3번과 5번 작업이 건너뛰어진 줄 알았다.** 그런데 아니었다.

```java
submit(() -> test(processTimes));

// 컴파일러가 보는 것
submit(() -> test(this.processTimes));   // ← 실행되는 순간에 꺼내 읽음
```

람다는 **값을 복사해 가는 게 아니라 `this`를 들고 간다.** 1초 뒤 깨어나서 그때의 필드값을 읽는다. 즉 모든 작업이 똑같이 생겼다. "1을 출력하는 작업"이 아니라 **"깨어난 순간의 `processTimes`를 출력하는 작업"**이다.

출력은 1초에 한 번(작업 시간), 필드는 0.5초에 한 번 증가 → 출력될 때마다 +2. 건너뛴 게 아니라 **그 숫자를 볼 타이밍에 깨어난 작업이 없었을 뿐**이다.

#### 지역 변수로 바꾸면 고정된다

```java
int taskId = processTimes;              // 스택에 있는 지역 변수
submit(() -> test(taskId));             // 제출 시점 값이 박힌다
```

<Callout type="tip" label="핵심:">
  비동기 작업에 값을 넘길 땐 **반드시 지역 변수로 스냅샷**해야 한다. 필드를 그대로 참조하면 "실행 시점의 값"이 들어가서, 로그와 실제 처리 대상이 어긋난다. 디버깅할 때 가장 헷갈리는 종류의 버그다.
</Callout>

### 6. 해결 — 쌓지 말고 건너뛴다

큐에 쌓지 않으려면, 이전 작업이 도는 중엔 **아예 submit하지 않으면** 된다.

```java
  private final AtomicBoolean busy = new AtomicBoolean(false);
  private final ExecutorService executorService = Executors.newSingleThreadExecutor();

  @Scheduled(fixedDelay = 500)
  public void dispatch() {
      System.out.println("실행시간 :" + LocalTime.now());

      if (!busy.compareAndSet(false, true)) {
          return;                                  // 처리 중 → 이번 틱은 버린다
      }

      executorService.submit(() -> {
          try {
              heavyTask();
          } catch (Exception e) {
              log.error("error ={}", e.getMessage());
          } finally {
              busy.set(false);                     // ★ 반드시 푼다
          }
      });
  }
```

**결과 값**

```bash
  실행시간 :11:29:29.407069
  실행시간 :11:29:29.907871   // +0.500초
  실행시간 :11:29:30.413428   // +0.505초
  실행시간 :11:29:30.917212   // +0.503초
  실행시간 :11:29:31.422855   // +0.505초
  실행시간 :11:29:31.928395   // +0.505초
```

주기는 3장과 똑같다.
**차이는 큐에 있다.** 3장에서는 계속 올라가던 큐 크기가 여기서는 0에 고정된다. 겉보기 로그가 같아서 놓치기 쉬운 지점이다.

#### compareAndSet이 반환하는 것

처음에 헷갈렸던 부분이다. 반환값은 "지금 값"이 아니라 **"바꾸는 데 성공했는지"**다.

```java
// busy.compareAndSet(false, true) 가 하는 일 (원자적으로)
  if (busy == false) {
      busy = true;
      return true;      // 성공 — 내가 자리를 차지했다
  } else {
      return false;     // 실패 — 이미 누가 쓰고 있다
  }
```

| busy 현재값 | 하는 일        | 반환      | `if (!결과)` |
| ----------- | -------------- | --------- | ------------ |
| `false`     | `true`로 변경  | **true**  | 통과 → 진행  |
| `true`      | 아무것도 안 함 | **false** | 진입 → 리턴  |

#### 왜 boolean이 아니라 AtomicBoolean인가

진짜 이유는 **가시성**이다.

```text
스케줄러 스레드  : busy를 읽는다
워커 스레드      : busy.set(false) 로 쓴다   ← 다른 스레드!
```

일반 `boolean`이면 워커가 `false`로 바꿔도 스케줄러 스레드는 자기 CPU 캐시의 낡은 `true`를 계속 볼 수 있다. 그러면 모든 틱이 `return`으로 빠져서 **작업이 영영 안 돈다.**

`AtomicBoolean`은 내부가 `volatile`이라 쓴 즉시 다른 스레드에 보인다.

<Callout type="tip" label="핵심:">
  `AtomicBoolean`이 여기서 주는 건 **원자성보다 가시성**이다. 스레드가 하나뿐이어도 필요하다. "쓰는 쪽과 읽는 쪽이 다른 스레드인가"가 판단 기준이다.
</Callout>

### 7. 숨은 함정 — busy를 못 푸는 경로
 
플래그를 푸는 책임이 어디 있는지가 생각보다 까다롭다. 실제로 이렇게 짰다가 한 번 멈췄다.
 
```java
if (!busy.compareAndSet(false, true)) {
    return;
}
 
executorService.submit(() -> {
    try {
        heavyTask();
    } catch (Exception e) {
        log.error("error ={}", e.getMessage());
    }
    // ← finally { busy.set(false); } 를 빠뜨림
});
```
 
첫 작업만 돌고 그 뒤로 전부 `return`이다. `busy`가 `true`로 박힌 채 아무도 안 풀어준다. **예외 로그 한 줄 없이 조용히 멈춘다.**
 
#### submit 자체가 실패하는 경우
 
`finally`를 넣어도 구멍이 하나 더 있다.
 
```java
if (!busy.compareAndSet(false, true)) return;
executorService.submit(...);   // ← 여기서 예외가 나면?
```
 
`submit()`이 터지면(executor가 종료됐다든지) 람다가 **아예 실행되지 않는다.** `finally`는 람다 안에 있으니 역시 실행되지 않는다. 같은 영구 정지다.
 
그래서 제출 성공 여부를 따로 들고 있어야 한다.
 
<CodeCompare>
  <CodePanel type="bad" title="위험 — 제출 실패 시 복구 불가">
    ```java
    if (!busy.compareAndSet(false, true)) return;
    executorService.submit(() -> {
        try { heavyTask(); }
        finally { busy.set(false); }
    });
    // submit이 터지면 busy가 영원히 true
    ```
  </CodePanel>
  <CodePanel type="good" title="안전 — 두 경로 모두 복구">
    ```java
    if (!busy.compareAndSet(false, true)) return;
    boolean submitted = false;
    try {
        executorService.submit(() -> {
            try { heavyTask(); }
            finally { busy.set(false); }   // 제출 성공 시
        });
        submitted = true;
    } catch (Exception e) {
        log.error("submit 실패", e);
    } finally {
        if (!submitted) busy.set(false);   // 제출 실패 시
    }
    ```
  </CodePanel>
</CodeCompare>
<Callout type="error" label="치명적:">
  플래그를 푸는 책임이 **두 군데로 나뉜다.** 제출에 성공했으면 람다가, 실패했으면 바깥 `finally`가 푼다. 둘 다 안 하면 영구 정지고, 둘 다 하면 이중 해제다.
  비동기 플래그를 쓸 땐 항상 **"이 플래그를 못 푸는 경로가 있는가"**를 먼저 따져야 한다.
</Callout>

### 8. 정리

| 단계                   | 주기 유지 | 다른 작업 영향 | 큐 적체 | 비고               |
| ---------------------- | --------- | -------------- | ------- | ------------------ |
| 그냥 둠 (`fixedDelay`) | 1.5초     | 같이 멈춤      | —       | 정의대로 동작한 것 |
| 풀 크기만 ↑            | 1.5초     | 안 멈춤        | —       | 내 주기는 그대로   |
| Executor로 분리        | 0.5초     | 안 멈춤        | 무한    | 보장이 하나 사라짐 |
| Executor + busy guard  | 0.5초     | 안 멈춤        | 고정    | 일부 틱을 버림     |

#### 이 패턴을 쓰면 안 되는 경우

건너뛴 작업은 **영영 실행되지 않는다.** 그러니 "모든 요청을 처리해야 하는" 작업에는 쓸 수 없다.

- **쓸 수 있음** — 최신 상태만 의미 있는 작업 (실시간 추정, 상태 동기화, 캐시 갱신)
- **쓰면 안 됨** — 건별 처리가 필요한 작업 (주문 처리, 정산, 메시지 전송)
  후자라면 큐를 쌓는 게 맞고, 대신 **소비 속도를 올리거나 생산 주기를 늦춰야** 한다. 밀리는 상태가 지속되면 애초에 주기 설정이 잘못된 것이다.
